WSGI

Web Server Gateway Interface

La couche qui connecte votre application Dash au serveur

Master 2 • Déploiement d'applications web

Le problème classique

  • Les serveurs web (Nginx, Apache) parlent HTTP
  • Votre code Python ne parle pas HTTP
  • Comment connecter les deux ?
  • Besoin d'une interface standardisée

Qu'est-ce que WSGI ?

WSGI = une spécification (PEP 3333) qui définit comment un serveur web communique avec une application Python.

  • Pas un serveur : c'est un contrat/interface
  • Pas un framework : c'est une norme
  • Permet la portabilité des applications

Architecture WSGI : Les deux côtés

Côté Serveur

Gunicorn, uWSGI, Waitress...

Écoute les requêtes HTTP, appelle l'application

Côté Application

Flask, Django, Dash...

Un callable Python qui reçoit les requêtes

La signature WSGI

def application(environ, start_response):
    # environ : dict avec les infos HTTP
    # start_response : callback pour envoyer réponse
    
    status = '200 OK'
    headers = [('Content-Type', 'text/plain')]
    start_response(status, headers)
    
    return [b"Hello World"]

Tous les frameworks Python doivent respecter cette signature

Le dictionnaire environ

  • REQUEST_METHOD : GET, POST, PUT, DELETE...
  • PATH_INFO : le chemin de la requête
  • QUERY_STRING : les paramètres d'URL
  • HTTP_* : tous les headers HTTP
  • wsgi.input : le corps de la requête (POST)

C'est tout ce dont vous avez besoin pour traiter la requête

Flux d'une requête WSGI

  1. Client envoie requête HTTP
  2. Serveur WSGI (Gunicorn) reçoit la requête
  3. Serveur crée le dict environ
  4. Serveur appelle application(environ, start_response)
  5. Application traite et retourne une réponse
  6. Serveur transmet la réponse au client

Avantages de WSGI

  • Standardisation : une seule interface pour tous
  • Flexibilité : swap serveur/framework indépendamment
  • Portabilité : votre Dash tourne partout
  • Performance : possibilité de workers multiples

Dash et WSGI

Quand vous créez une app Dash, elle est un objet WSGI-compliant : 

import dash

app = dash.Dash(__name__)

# app.server est une application WSGI Flask
# (Dash utilise Flask en dessous)

Vous pouvez donc utiliser n'importe quel serveur WSGI !

Architecture typique : Nginx + Gunicorn + Dash

Client HTTP
    ↓
Nginx (port 80/443)
    ↓
Gunicorn WSGI (port 8000)
    ↓
Votre app Dash
    ↓
Réponse HTML/JSON

Nginx gère les connexions, Gunicorn gère Python, Dash gère la logique

Serveurs WSGI courants

  • Gunicorn : simple, populaire, production ✓
  • uWSGI : puissant, complexe, flexible
  • Waitress : pur Python, pas de dépendances C
  • mod_wsgi : intégré à Apache

Pour Dash en production : Gunicorn est le meilleur choix

Démarrer une app Dash avec Gunicorn

gunicorn --bind 0.0.0.0:8000 app:server

Où app = le fichier Python et server = la variable WSGI

Note : dans Dash, utilisez app.server (c'est l'objet Flask sous-jacent)

Configuration Gunicorn avancée

  • --workers 4 : nombre de workers (processus)
  • --threads 2 : threads par worker
  • --worker-class gthread : threading
  • --timeout 60 : timeout en secondes

Règle : workers = (2 × CPU cores) + 1

Configuration Nginx pour Dash

server {
    listen 80;
    server_name example.com;

    location /app/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
    }
}

L'URL Dash doit correspondre avec url_base_pathname

Bonnes pratiques de déploiement

  • Toujours utiliser Nginx devant Gunicorn
  • Au minimum 2 workers Gunicorn
  • Monitorer la consommation mémoire/CPU
  • Logs séparés : Nginx et Gunicorn
  • Utiliser systemd pour gérer Gunicorn
